The game, in brief
underward is a mobile-first, touch-driven dungeon crawler that runs from a single HTML page, played by opening a URL on a phone (hosted on GitHub Pages). No build step, no libraries, no frameworks — plain scripts sharing one global namespace called Delve. Player taps to move, walks into monsters to fight, levels up and picks traits, and spends "shards" between runs on permanent upgrades in a hub. Two areas exist: Upper Ruins (floors 1-10) and The Blackvein (floors 11-20); nothing beyond floor 20. Bosses on floors 10 and 20. Around 100 items, a monster roster, six upgrade trees, and abilities. Progress saves to the phone's localStorage under the key "underward_save_v3". There are 26 script files plus index.html, test.html, a manifest, and an icons folder.

Files and conventions worth knowing

· architecture.md — the project hand-off/architecture reference. Its sections describe the file map, load order, editing protocol, and known weak points.
· test.html — a 12-section self-test page. Requires being served over http (it won't work opened from a file). It is the source of truth for whatever it checks.
· js/ — 26 scripts; js/content/ holds data-only "content" files (monsters, items, biomes, traits, progression, boss sprites); everything else is engine logic.
· index.html loads the scripts in a specific order; that order is load-bearing and documented.
· Debug tools: add ?v=N to the URL after any upload (busts phone caching); ?debug=1 for an in-game debug panel; ?diag=1 for a tap-diagnostic overlay.
· The project's documented editing protocol: give partial edits as BEFORE/AFTER blocks with anchor lines, or hand over whole files for full rewrites; never rename a variable inside a replacement block; if a function moves between files, both files must ship together. Q4 - The battle log. Answer: it should be openable on demand, but kept minimised/hidden when not in use so it takes no screen space, and expandable so the player can look and scroll through it (Currently the button that opens it is unreachable, because the bar holding it is hidden and nothing ever reveals it.)

Q5 - Legendary gear. Answer: follow how the genre normally does it. Rarity should be governed by how deep the player is AND their luck attribute. Legendary should be theoretically possible from floor 1 but so unlikely there that it's a near-impossibility, becoming steadily more likely the deeper you go and the higher your luck. The owner's own words: the game's unique selling point is the between-runs shard upgrade system, so a robust, thorough set of permanent upgrades matters a lot.

Q6 - How much to change in the first batch. Deferred to the AI. Decision taken: work in small, focused batches (one area at a time) rather than everything at once, so each change is made carefully and the owner isn't testing many things simultaneously.

Q7 - The small cosmetic clean-ups. Answer: do them as we go, because the owner wants everything tidied and ready before the next major task (see "Future task" below).

Q8 - How changes are delivered to the files. The owner asked for options and a recommendation. Explained: an AI in this setup cannot write to the device (terminal issue above) and cannot push to GitHub. Real options: (A) whole-file replacement — the AI supplies the complete finished file and the owner pastes it over the old one (recommended, safest on a phone); (B) small before/after snippets — less text but fiddly and easy to misplace on a phone. Q9 - Testing. The owner does NOT want to run test.html after every change; they'd rather batch several related changes and test once. BUG THE OWNER FOUND (shards were banked mid-run): the owner earned a couple of shards on a quick test, refreshed the page, and the shards were still there - even though refreshing takes you out of the dungeon without dying. Cause: four places wrote straight into the saved shard total the moment shards were earned (every kill, the floor-clear bonus, the gold-to-shard conversion, and the boss bonus) and saved to storage immediately. So a refresh - or the phone closing the tab - kept everything earned, and dying cost the player nothing. Shards are earned during a run and only become yours once the run ends.

THE FIX (Batch 10): run-earned shards now live only in the run's own counter and are never in the saved file while you are playing. One new function banks them at a "commit point", and there are exactly three: dying, retreating, and beating a ward boss. The HUD still counts up as you earn, so no feedback the player had has been lost - what changed is that a refresh now loses the run's earnings exactly as it loses the run. Files touched: js/combat.js, js/rewards.js, js/state.js, js/ui.js, architecture.md, cp.txt. One wording change to flag: the "escaped" screen said "N shards from gold" and now says "N shards banked", because it reports everything the run banked rather than only the gold conversion.

BATCH 11 - THE TITLE SCREEN (new file js/menu.js) - WRITTEN TO DISK, NOT YET UPLOADED OR PLAYED

What the owner asked for: a visually appealing title screen showing the game's name, opening into a menu (start a run / select a save file / settings), built with code for now and replaced later with the owner's own visuals.

What was built: a new file js/menu.js owns the front end, and the game now opens on the title screen every time. The wordmark is styling only - black letters, a thick acid-green outline that slowly pulses, plus a second stroke that drifts so the outline appears to move (the owner's description). Two buttons: CONTINUE, and SETTINGS. On a completely fresh save the first button reads BEGIN, so a new player never meets a CONTINUE that leads nowhere. SETTINGS controls the same four sound settings as the in-run pause menu through the same sound code - a second view of one set of settings, never a second copy.

Deliberate technical choices worth knowing:
- The wordmark is styling only, with no canvas drawing, so the map and every tap calculation are untouched - and swapping in the owner's own visuals later means replacing one style block and one markup block in index.html.
- Genuinely jagged letterforms need a font file, and this project ships none, so the "jagged rather than rounded" feel is approximated with a heavy weight, tight letter spacing and a doubled outline. Worth knowing before judging the letters.
- The title's settings controls use their own names (titleMuteBtn, titleVolumeSlider, and so on) rather than reusing the pause menu's. Deliberate: the game's UI file looks those names up when it loads, so a name clash would silently break the pause menu's controls with no error shown anywhere.
- The title screen had to be added to the game's two "which screens are open" lists and to the test page's file list, or it would either fail to close or let taps pass through to the map behind it.
- One tidy-up made at the same time: the test page's overlay list had the level-up screen mis-spelled as levelUpScreen (harmless - the entry just never matched). Now corrected. See checklist.txt, "unresolved nit", for the related item that was deliberately left alone.

CONTINUE and resuming a run (the owner's question): CONTINUE was built with a deliberate hook for resuming. Today it always leads to the hub, because nothing saves an in-progress run yet. When run-resume is built it will expose the two names the hook looks for, and CONTINUE will start resuming with no change to the title screen at all. On the floor question: resuming must recreate the IDENTICAL floor, never generate a fresh version of the same floor number - a fresh layout would hand back every chest, barrel and monster the player had already cleared, which is an endless loot farm. Identical is the more expensive option, since it needs either the finished map or a "seed" stored in the save, so it remains a batch of its own.
